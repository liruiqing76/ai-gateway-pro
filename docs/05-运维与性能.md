# 运维与性能

## 1. 日志

### 日志级别

| 环境 | 级别 | 输出示例 |
|------|------|---------|
| 开发（`GW_DEBUG=true`） | DEBUG 全部 | 每条请求的选路日志、转发细节 |
| 生产（默认） | INFO+ | 上游错误、熔断触发、编排告警 |

由 `backend/main.py` 的 `logging.basicConfig` 统一配置，logger 命名空间 `gateway.*`：

| Logger | 覆盖范围 |
|--------|---------|
| `gateway.proxy` | 转发、故障转移、候选选择 |
| `gateway.orchestrate` | 编排阶段执行、失败告警 |
| `gateway.trace` | 链路追踪持久化 |
| `gateway.aliases` | 别名管理操作 |
| `gateway.traces` | 链路日志查询 |

### 关键日志点（排障时 grep）

```bash
# 上游错误
grep "upstream" backend.log
# 流式故障转移
grep "stream fallback" backend.log
# 熔断触发
grep -i "circuit\|熔断" backend.log
# 编排阶段失败
grep "relay stage\|review" backend.log
```

## 2. 请求链路追踪

每个请求产生一条 `request_traces` 记录，是排障第一入口：

```bash
# 通过 API 查询（管理面板「请求链路」页）
curl "http://127.0.0.1:8765/api/traces?limit=10&success=false" \
  -H "Authorization: Bearer <你的APIKey>"

# 统计概览
curl "http://127.0.0.1:8765/api/traces/stats?days=7" \
  -H "Authorization: Bearer <你的APIKey>"

# 清理 30 天前日志
curl -X DELETE "http://127.0.0.1:8765/api/traces/cleanup?days=30" \
  -H "Authorization: Bearer <你的APIKey>"
```

### 数据量控制

- 每条记录约 0.5-1 KB（含 stages_detail JSON）
- 建议每周用 `/api/traces/cleanup` 清理一次，或接入 cron
- 链路日志仅影响调试与统计，不影响请求转发（异步写入，失败不影响主流程）

## 4. 性能特征

### 设计上的性能点

| 机制 | 效果 |
|------|------|
| httpx 全局连接池 | 上游连接复用，避免每请求新建 TCP/TLS |
| SQLite 同步 + 短 session | 管理操作低频，无瓶颈 |
| trace/日志异步写入 | 主请求链路不受持久化拖累 |
| 熔断缓存查询 | `is_open` O(1) 字典查询 |

### 基准测试

项目内置性能基准测试（`tests/test_performance.py`），覆盖关键路径：

| 测试 | 场景 | 基准（宽松阈值） |
|------|------|-----------------|
| `pick_available_models` 50 候选 | 路由选择 | < 500ms |
| 熔断器 10k 次操作 | 状态机 | < 2s |
| 质量调度器 10k 次记录 | 滑动窗口 | < 2s |
| 转发引擎 return_result 纯函数 | 响应构造 | < 1s（100k 次） |
| 流式转发 chunk 组包 | SSE 打包 | 每 chunk < 0.5ms |

> 阈值为宽松基线，防止 CI 波动误报；可自行收紧用于回归对比。

运行：

```bash
pytest tests/test_performance.py -v
```

### 性能调优建议

1. **减少上游延迟**：路由组策略改 `fastest`
2. **减少上游失败**：定期清理不稳渠道/模型（看请求链路成功率）
3. **提高吞吐**：`uvicorn --workers 2`（多进程共享 SQLite 需注意写锁）
4. **磁盘 IO**：SQLite WAL 模式（`PRAGMA journal_mode=WAL`）能显著提升并发写

## 5. 常见运维问题

### Q1: 所有请求都失败「所有候选模型均失败」

1. 查链路日志：`GET /api/traces?success=false`
2. 看 `error_msg`：`upstream 401` = 密钥失效；`upstream timeout` = 上游网络；`connection error` = 上游不可达
3. 到「渠道管理」点「获取模型列表」验证密钥仍有效

### Q2: 某个模型经常被跳过

查 `circuit_breaker_hit=true` 的链路记录 → 该模型熔断中（60s）或有失败的累计计数。「路由组」页「检测可用性」可主动验证。

### Q3: 流式响应突然中断

SSE 中途断开说明上游流中出错（超时/连接重置）。看后端日志 `stream` / `upstream` 关键字。可调大 `GW_PROXY_TIMEOUT_SECONDS`。

### Q4: 编排「最后一个阶段失败返回 502」

relay 全阶段失败或 review 主模型失败。降级策略：改回单模型或换组名；查 `stages_detail` 看哪级失败。

## 6. 升级与迁移

1. 备份数据库
2. 拉取新代码，`pip install -r requirements.txt` 更新依赖
3. `create_tables()` 自动补建新表（幂等，不删数据）——新增表结构不需要手工迁移
4. 重启服务
