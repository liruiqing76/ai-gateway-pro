# 白嫖渠道收编路线图（参考 dsh-our-free-model）

> 本文档基于对 DSH 插件 `dsh-our-free-model` v2.1.0「十三个白嫖渠道」实现的逆向调研，
> 给出把各 AI 编程工具的免费额度收编进本网关的可行性分级、推荐顺序与落地设计。
> 调研对象：`C:\Users\leslie\.dsh\profiles\desktop\node_modules\dsh-our-free-model`
> （渠道实现主体在其 `vendor/channel-pack/pack.js`，源自 gitee.com/iJetLi/deepseek-harness-codearts，MIT）。

---

## 1. 为什么值得做

本网关的定位是「聚合所有模型的免费额度」。当前上游全部是**公开 API 面**（NVIDIA / 魔搭 /
OpenRouter / OpenCode Zen / b.ai），而 dsh-our-free-model 证明了另一类上游——
**各 AI 编程工具（IDE 插件 / CLI）自带的账号免费额度**——也可以被网关统一收编：

- 模型质量高：DeepSeek-V4.1-Flash、Kimi-K3、GLM-5.3、GPT-5.6 系，多数 1M 上下文；
- 额度可观：多数渠道每日签到送积分，免费模型不扣积分；
- 与本网关模型完全兼容：每渠道一个 Provider，走既有路由组 / 熔断 / 加权分发。

## 2. 十三渠道复刻可行性分级

| 级别 | 渠道 | 说明 |
|------|------|------|
| **A 可直接复刻** | **cline**、**buddy（CodeBuddy）**、workbuddy、lobsterai | 登录纯 HTTP 可编程（设备码/state 轮询），推理端点标准 OpenAI 兼容 |
| **B 需逆向/复杂流程** | codearts（DPoP+华为云 HMAC 签名）、qoder 明文端点（machine_token）、trae（自定义协议）、loomy（微信扫码）、raccoon（公众号扫码） | 登录需浏览器人工介入或签名链路较长，推理端点多是 OpenAI 形状 |
| **C 强绑定 wasm/设备指纹** | qoder 加密端点（wasm COSY 签名）、zcode（阿里云 captcha + 常驻 chromium） | 不建议复刻，投入产出比差 |
| **D Anthropic 形状需转换** | **minimax**（OAuth2 设备码 + Anthropic Messages 端点）、zcode 兼 C、gemini（generateContent 内部协议） | 需要协议转换层——**本网关已有 anthropic_codec.py，正好复用反向** |

另有两个**零成本 A+ 级入口**（插件自有车道，不在 13 渠道之列）：

- **Kilo 免费池**：`https://api.kilo.ai/api/gateway/chat/completions`，**无任何认证**，免费模型清单 GET `/models` 的 `isFree`；
- **OpenCode Zen 匿名车道**：`https://opencode.ai/zen/v1/*`，`Authorization: Bearer public`（本网关 ZEN_AUTO_SYNC 已部分覆盖，可对齐免费档口径）。

## 3. 首批推荐

1. **Cline**（A 级最佳）
   - 登录：WorkOS 设备码流，全程纯 HTTP——`POST api.workos.com/user_management/authorize/device` → 用户浏览器确认 → 轮询 `/authenticate` → `POST api.cline.bot/api/v1/auth/register` 兑换，token 前缀 `workos:`，可刷新；
   - 推理：`POST api.cline.bot/api/v1/chat/completions`（标准 OpenAI SSE），附加头 `HTTP-Referer: https://cline.bot` / `X-Title: Cline` / `X-CLIENT-TYPE: cline-sdk`；
   - 免费模型：`cline-free/` 前缀 3 个（Space Bunny Alpha 1M ctx、mimo-v2.6-flash、muse-spark-1.3-contributor）。
2. **CodeBuddy（腾讯）**（A 级，额度最慷慨）
   - 登录：`POST copilot.tencent.com/v2/plugin/auth/state` → 浏览器开 authUrl 一次 → 轮询 `GET /v2/plugin/auth/token?state=`；
   - 推理：`POST copilot.tencent.com/v2/chat/completions`（标准 OpenAI SSE），头 Bearer + `X-IDE-Name/Type/Version` + UA `CodeBuddyIDE/1.106.1`；
   - 模型：GET `/v3/config`；免费模型不扣积分。
3. **MiniMax Code**（D 级备选，验证协议转换复用）
   - 登录：标准 OAuth2 设备码（`account.minimax.cn/oauth2/device/code` + `/oauth2/token`）；
   - 推理：`POST agent.minimax.cn/mavis/api/v1/llm/v1/messages` —— **Anthropic Messages 形状**。`anthropic_codec.py` 的 `from_anthropic_request` / `openai_completion_to_message` 可反向复用（OpenAI 请求 → Anthropic 上游、Anthropic 流 → OpenAI chunk 流）。

## 4. 落地设计（对齐现有架构）

### 4.1 数据模型：不动表结构

沿用现有 `Provider` 模型，约定：

- `name`：渠道 id（`cline` / `codebuddy` / `minimax` …），与路由组 `渠道名-模型名` 前缀约定天然兼容；
- `base_url`：推理端点前缀（如 `https://api.cline.bot/api/v1`）；
- `api_key_encrypted`：AES-256-GCM 加密的 JSON 凭据包 `{access_token, refresh_token, expires_at, machine_id?, …}`——与现有 `decrypt_secret` 链路零改动；
- `models`：渠道免费模型清单（登录/刷新时拉取）。

### 4.2 新增模块：`backend/core/channel_auth/`

每渠道一个登录器（纯函数式，方便测试）：

```
backend/core/channel_auth/
    __init__.py       # registry: {channel_id: login(client) -> credentials_json, refresh, headers}
    cline.py          # WorkOS 设备码 + register 兑换 + refresh
    codebuddy.py      # state→authUrl→轮询 token
    minimax.py        # OAuth2 设备码
```

- 登录流程产出「给用户看的一步」（如设备码确认链接），由前端设置页引导；
- `headers(channel, credentials, model)` 生成渠道所需的附加头（X-IDE-* / HTTP-Referer / 双 token 头等）；
- 刷新器挂在现有 APScheduler 上（参考 zen_sources 的保活模式），到期前续期。

### 4.3 转发层：最小改动

`core/proxy.py` 的 `forward_*` 目前只加 `Authorization: Bearer`。给 Provider 加一个可选
`extra_headers` JSON 列（或按渠道 id 查 channel_auth 注册表现算），登录器产出的头在转发时
合并进去。**不动现有签名**，只加一个 `headers.update(...)` 钩子。

协议是 Anthropic 形状的渠道（minimax/zcode）在 `forward_*` 之前套 `anthropic_codec` 的
反向转换即可——与本次新增的 `/v1/messages` 端点共用同一套编解码器。

### 4.4 UI：渠道模板池

「添加渠道 → 模板一键添加」已有 provider_templates 机制，白嫖渠道作为新模板加入，
模板触发对应登录器流程（设备码页面 / authUrl 跳转），完成后自动写 Provider 行 + 拉模型清单。

## 5. 风险与合规（必须写进产品口径）

- **上游条款由使用者遵守**：这些渠道本质是各厂 IDE/CLI 的私有接口，插件全部在伪装官方客户端身份（CodeBuddyIDE/1.106.1、antigravity/4.3.0 等），属 ToS 灰色地带；
- **个人自用、随时失效**：免费额度可随时收回，反滥用机制（模型级限流、captcha、设备指纹）可能随时收紧——**不写入任何商业承诺**；
- Kilo 免费池官方声明 prompt 可能被记录，勿发敏感内容；
- 建议默认关闭、显式开启，并在渠道卡片上明示来源与风险。

### MiniMax Code 渠道契约(2026-10-24 真机核实)

国内站 `account.minimax.cn`(OAuth) + `agent.minimax.cn`(推理/签到), 客户端
`client_id=mcode-public` / `audience=agent-backend` / `scope=agent.default`。

- 设备码 `POST {account}/oauth2/device/code`(form) body
  `{client_id, scope, audience, code_challenge, code_challenge_method:"S256"}` →
  `{device_code, user_code, verification_uri(_complete), expires_in, interval}`;
  PKCE verifier = 32 随机字节 base64url, challenge = sha256(verifier) base64url
- 轮询/续期同端点 `POST {account}/oauth2/token`(form):
  轮询 `grant_type=urn:ietf:params:oauth:grant-type:device_code` + `device_code`
  + `code_verifier`; 续期 `grant_type=refresh_token` + `refresh_token`
  + `client_id`/`scope`/`audience`
- ⚠ **refresh_token 一次性轮换**: 刷新成功即刻作废旧 refresh_token(再用回
  `400 invalid_grant "this refresh token can no longer be used"`) →
  续期后必须**立刻回写 Provider**(`checkin._persist_refreshed_credentials`)
- 模型 `GET {api}/mavis/api/v1/models` → `providers[].config.{models,model_order}`
  (实测 `MiniMax-M3` / `MiniMax-M3.1-Flash`「订阅限免」/ `M3.1-Flash-Preview` /
  `M2.7-highspeed` / `M2.7`, 512k~1M ctx, 128k 输出, M3 系支持 vision)
- 推理 `POST {api}/mavis/api/v1/llm/v1/messages` 是 **Anthropic Messages 形状**
  (不是 OpenAI) → 网关侧由 `channel_auth/minimax_wire.py` 双向桥:
  请求 OpenAI→Anthropic(`to_anthropic_body`), 响应 Anthropic SSE→OpenAI
  chunk(`AnthropicToOpenAISse`), 走 `channel_transform` 变换渠道通道
- 签到 `GET {api}/minimax-cloud/api/v1/signin/status?timezone_id=Asia/Shanghai`
  → `{data:{scene, days:[{day_no,points,bonus_points,status,is_today}]},
  base_resp:{status_code,status_msg}}`; 领取 `POST .../signin/claim` body `{}` →
  `data.claim_result`(1=Claimed / 2=AlreadyClaimed) + `data.points` + `data.panel`
- 信封 `base_resp.status_code != 0` = 业务错(HTTP 可能是 200)

### 实测记录(2026-10-24, 本机出口 123.139.161.30/CN)

- **渠道路由组自愈(2026-10-25 01:10, 真机发现的不一致)**:
  体检发现 `workbuddy` 渠道 31 个模型、同名路由组只有 30 个 —— 因为组只在**登录那一刻**
  建一次, 上游后来新增的 `gpt-6-luna` 没进组, 客户端按组名调用就永远漏掉它。
  修法 `backend/api/channels.py::_reconcile_channel_groups` + `_merge_group_models`:
  `GET /api/channels` 时做增量对齐 —— 组内本渠道前缀条目按当前清单重建(下线模型自动剔除),
  **其它条目(用户手动加进组的)原样保留**, 稳态零写入(比对无差异不 commit)。
  真机复验: workbuddy 组 30 → **31**, 体检脚本"问题"清单由 1 条变 0 条。
- **额度恢复时刻的显示要自己过期(2026-10-25 01:12)**:
