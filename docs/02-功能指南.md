# 功能指南

本文档逐个介绍网关的全部功能、配置方式与调用方法。

---

## 渠道管理

### 概念

「渠道」= 一个上游 AI 平台账号（如 NVIDIA Build、魔搭、SenseNova）。网关聚合所有渠道，对外统一路由。

### 支持的模板

| 模板 | Base URL | 特性 |
|------|----------|------|
| NVIDIA | `https://integrate.api.nvidia.com/v1` | 免费额度约 1000 次/月 |
| 魔搭 ModelScope | `https://api-inference.modelscope.cn/v1` | 免费额度按日/周 |
| SenseNova 商汤 | 平台 URL | 新用户赠送额度 |
| 自定义 | 任意 OpenAI 兼容端点 | 支持自建代理 |

### 操作

- **添加**：管理面板「渠道管理」→ 手动填写或「模板一键添加」
- **编辑**：修改 Base URL / 密钥 / 模型列表
- **禁用/启用**：禁用的渠道不参与路由
- **删除**：删除前需确认（会级联清理用量引用）
- **模型管理**：渠道详情里可逐个禁用不可用/不想用的模型

### 安全存储

API 密钥使用 **AES-256-GCM** 加密后落库（`api_key_encrypted` 字段），数据库中不存明文。请求转发时才解密。

### 校验与模型拉取

创建/编辑渠道时后端会：

1. 用提供的密钥请求 `GET {base_url}/models`，验证密钥有效性
2. 拉取模型列表自动填入 `models` 字段
3. 若请求失败，允许保存但标记模型列表需手动填写

## 路由组

### 概念

路由组是一组「能力相近」的模型集合。客户端在 `model` 字段填**组名**，网关从组内挑选最优模型执行，组内模型故障时自动切换到同组其他模型。

### 内置路由组（自动分类）

创建渠道后自动按模型名归类：

| 组名 | 中文别名 | 匹配规则 | 适用 |
|------|---------|---------|------|
| `quick` | `快速` | qwen-8b、llama-3.2-3b、glm-4-flash、`*-8b`/`*-7b`/`*-3b` | 轻量任务、快速响应 |
| `high_quality` | `日常` | glm-4/5、qwen-max/plus、deepseek-v3/r1、claude、gpt-4o | 复杂推理/创作 |
| `vision` | `识图` | qwen-vl、glm-4v、gpt-4o-vision、internvl | 多模态视觉 |

客户端填中文组名（`model: "快速"`）也会自动映射到英文键。

### 用户自定义路由组

「路由组」页面可：

- 手动勾选模型创建自定义组
- 设置组策略（quality / fastest / stable）
- 检测组内模型可用性（`POST /api/routers/check-availability`）

### 调用方式

```python
# 直接用组名
client.chat.completions.create(model="quick", messages=[...])
# 中文组名同样支持
client.chat.completions.create(model="快速", messages=[...])
```

### 特殊自动组

`auto-router-1m`：当某个模型上下文长度 ≥ 1M（如 glm-5.2），自动归入此组，防止长上下文请求被路由到小上下文模型。

## 路由策略

路由组可按策略排序候选模型，决定「优先尝试谁」：

| 策略 | 排序规则 | 适用场景 |
|------|---------|---------|
| `quality`（默认） | 质量分最高优先，同分按延迟 | 对回答质量敏感 |
| `fastest` | 延迟最低优先 | 对响应速度敏感（如聊天） |
| `stable` | 成功率最高优先，同分按延迟 | 对稳定性敏感（如生产 API） |

### 质量分计算

质量分由调度器维护，基于最近 20 次请求的滑动窗口（`QualityTracker`）：

```
质量分 = (成功数 - 失败数×0.5 - 错误数×1.0) / 总数 × 置信度
置信度 = min(请求数 / 窗口, 1.0)
```

- `ok` 记 +1 分
- `fail`（上游 4xx/5xx）记 -0.5
- `error`（网络错误/异常）记 -1.0
- 请求数越多，置信度越高，评分越可信

熔断中的模型永远排在最后（即使质量分最高）。

## 熔断与故障转移

### 熔断器（Circuit Breaker）

每个 `(渠道, 模型)` 组合一个熔断状态机：

```
正常 → 连续失败≥3次 → OPEN(熔断60s) → 到期进入半开 → 成功→正常 / 失败→重新OPEN
```

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `FAIL_THRESHOLD` | 3 | 连续失败触发熔断的阈值 |
| `RECOVERY_SECONDS` | 60 | 熔断冷却时长（秒） |
| `RATE_LIMIT_BASE` | 30 | 429 限流首次冷却（秒） |

熔断中的 `(渠道, 模型)` 不会被选为主候选；只有在所有非熔断候选都失败时才作为兜底。

### 自动故障转移（Failover）

- **非流式**：候选按策略排序后逐个尝试，前一个失败立即尝试下一个，全部失败返回 502
- **流式**：连接前先验证首个 SSE chunk 合法性；连接失败/数据格式错误会在**返回任何数据给客户端之前**切换下一个候选
- **编排**：每个阶段内部同样执行候选级故障转移

### 失败记录

每次失败（超时、4xx、5xx、非 JSON、空 choices）都会：

1. `circuit_breaker.record_fail(key)` → 累计失败计数
2. `quality_tracker.record(key, "fail"/"error", latency)` → 更新质量分
3. 若失败数达到阈值 → 熔断开启

### 限流冷却（429）

命中上游 429 时：

```
冷却 = 30s → 60s → 120s → 240s → 300s（封顶）
```

连续 429 冷却时间指数翻倍，成功后重置。限流命中的 `(渠道, 模型)` 在冷却期内被跳过。

## 多模型编排

编排引擎让多个模型**协作**完成一次请求，`model` 字段用特殊格式声明：

### Relay（接力）

```
relay:组A/组B/组C...   最多 5 级
```

- 第一级用原始 prompt
- 后续每级注入「上一级输出 + 上下文交接 system 消息」
- 适合：让强模型精修弱模型的输出、分步推理

```python
client.chat.completions.create(
    model="relay:quick/high_quality",
    messages=[{"role": "user", "content": "写一篇产品文案"}],
)
```

### Review（审阅）

```
review:主模型/审阅模型   恰好 2 级
```

- 主模型生成初稿
- 审阅模型检查错误/遗漏/表达后输出修订版
- 审阅失败时回退返回初稿

```python
client.chat.completions.create(
    model="review:high_quality/quick",
    messages=[{"role": "user", "content": "写一段英文邮件"}],
)
```

### 流式编排（SSE）

编排请求同样支持 `"stream": true`：

- 前序阶段（需要完整输出作为下一级输入）内部非流式执行
- **最后一级以 SSE 流式输出**到客户端

```python
stream = client.chat.completions.create(
    model="relay:quick/high_quality",
    stream=True,
    messages=[{"role": "user", "content": "写个故事"}],
)
for chunk in stream:
    print(chunk.choices[0].delta.content or "", end="")
```

### 阶段内故障转移

每个阶段内部等价于一次独立代理请求：按策略取候选 → 逐个尝试 → 全部失败则该阶段跳过（relay）或回退上一级结果（review）。

## 流式输出

### 单一模型流式

`"stream": true` 时返回标准 OpenAI SSE 事件流：

```
data: {"id":"...","choices":[{"delta":{"role":"assistant","content":"你好"}}]}
data: {"id":"...","choices":[{"delta":{"content":"世界"}}]}
data: [DONE]
```

**故障转移优化**：流式请求在**返回第一个 SSE 事件前**完成候选验证（预读首个 chunk），因此上游连接失败时客户端不会收到半截响应，而是静默切换到下一个候选。

响应头会带上实际使用的渠道/模型：`X-Provider`、`X-Model`。

## 模型别名

### 概念

用户自定义「别名 → 目标」映射，把难记的模型名变成简单名称。**请求时别名自动解析为路由组或具体模型**。

### 典型场景

| 别名 | 目标 | 效果 |
|------|------|------|
| `gpt-4` | `high_quality` | 老客户端填 gpt-4，自动走高质量组 |
| `fast` | `quick` | 简短的快速模型别名 |
| `v` | `vision` | 单字母视觉别名 |

### 使用方式

管理面板「模型别名」页新增映射后，客户端直接用别名：

```python
client = OpenAI(base_url=".../v1", api_key="你的Key")
resp = client.chat.completions.create(model="gpt-4", messages=[...])  # → 实际路由到 high_quality 组
```

### API

完整的 CRUD + 批量接口见 [API 参考 - 模型别名](03-API参考.md#模型别名)。

## 请求链路日志

每次请求结束后写入 `request_traces` 表，完整记录决策链路：

| 字段 | 含义 |
|------|------|
| `original_model` | 客户端原始 model 字段 |
| `resolved_model` | 别名/路由组解析后的目标 |
| `provider_name` / `model_name` | 实际使用的渠道与模型 |
| `selection_strategy` | 使用的排序策略 |
| `selection_reason` | 选择原因摘要 |
| `circuit_breaker_hit` | 是否命中熔断 |
| `rate_limit_hit` / `cooldown_seconds` | 是否限流及冷却时长 |
| `latency_ms` | 总延迟（毫秒） |
| `success` / `error_msg` | 结果与错误 |
| `stages_detail` | 编排各阶段的明细（JSON） |

### 分析场景

- **为什么慢**：看 `latency_ms` 与 `stages_detail` 各阶段耗时
- **为什么换了模型**：看 `selection_reason`、`circuit_breaker_hit`
- **限流排查**：筛选 `rate_limit_hit=true` 的请求，看冷却时长
- **策略调优**：对比不同策略下同请求的成功率与延迟

查询/统计/清理接口见 [API 参考 - 请求链路](03-API参考.md#请求链路)。

## 用量统计

管理面板「仪表盘」与 `/api/usage` 提供：

- **今日调用次数 / 额度**（`quota_used_today` vs `quota_daily`）
- **Token 消耗**（prompt / completion / total）
- **最近用量明细**（每次请求的渠道、模型、延迟、Token）

额度控制：`check_quota` 校验每日调用次数，超限返回 429/403。

## 设置中心

管理面板侧边栏「设置」页，包含：

### 界面语言

- 简体中文 / English 随时切换（顶栏下拉与登录页也有入口）
- 偏好保存在浏览器本地（`gw_locale`），默认跟随系统语言
- Element Plus 内置文案（表格空态、时间选择器等）同步切换

### 开机自启动（仅桌面客户端）

- 一键开关：在 Windows「启动」文件夹写入/删除快捷方式，指向当前 exe
- 仅打包后的 exe 支持该功能；源码模式（`python desktop/desktop.py`）下开关置灰并提示
- 开启后登录 Windows 自动拉起智能网关，配合定时签到可保证不缺席
- 接口报错带 `error_code`（`not_packaged` / `exception`），前端按当前语言展示
