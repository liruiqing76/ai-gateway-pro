## 3. 一次请求的完整决策链路

以 `POST /v1/chat/completions`（`model: "high_quality"`，非流式）为例：

```
1. 鉴权         get_current_user_from_api_key 校验 API Key
2. 配额         check_quota 校验今日次数
3. 装载上下文    查询渠渠道(enabled=true) / 路由组 / 别名 / 路由策略 → 关闭 session
4. 解密密钥     decrypt_secret 解密每个渠道的 API Key
5. 解析模型     parse_pipeline → 否；别名表无命中；normalize_group_name("high_quality")
6. 选候选       pick_available_models:
                 - 组内模型 = {NVIDIA-xxx, 魔搭-yyy, ...}
                 - 排除熔断中的 → 按 strategy(quality): 质量分降序、延迟升序
7. 兜底候选     全渠道模型列表（放宽匹配）
8. 逐个尝试     对候选1:
                 forward_non_stream → 上游4xx → record_fail + 质量分降 → 候选2
                 forward_non_stream → 200 → record_success + 质量分升
9. 记录         UsageLog + quota_used_today+1 + trace 落库
10. 返回        JSONResponse (model 字段标记为 "NVIDIA · deepseek-v3")
```

### 流式路径差异

- 第 6-8 步用 `forward_stream`
- 连接后预读首个 SSE chunk 验证有效性，无效视为失败切换候选
- 成功 → 直接 `StreamingResponse`，`X-Provider`/`X-Model` 头标记实际渠道/模型

### 编排路径差异

- 第 5 步命中 `relay:` / `review:`
- 每个阶段内部重复步骤 6-8（阶段级故障转移）
- 非流式：全部阶段执行完返回最终响应
- 流式：前 N-1 阶段非流式，最后一级流式输出

## 5. 关键设计决策

### 5.1 为什么密钥用 AES-256-GCM 而非明文

数据库是 SQLite 文件，明文密钥一旦泄露所有渠道额度都危险。GCM 提供机密性 + 完整性校验，密钥本身来自配置文件/环境变量，不在库中。

### 5.2 为什么路由选择用「质量分 + 熔断」双机制

- 熔断器处理**短时突发**：连续失败立刻隔离，避免反复打爆故障上游
- 质量分处理**长期趋势**：成功率低的模型在候选排序中持续靠后，但不至于一票否决（熔断中才是最后兜底）

两者叠加 = 快速响应故障 + 长期自适应优化。

### 5.3 为什么流式故障转移靠「预读首 chunk」

HTTP 连接成功 ≠ 请求成功（上游可能 200 后立即挂掉，或返回非 SSE 内容）。在返回任何数据给客户端前预读并校验首个 chunk，把「假成功」识别为失败，从而实现干净的无缝切换。

### 5.4 为什么编排最后一级才流式

relay/review 的每一级都需要上一级的**完整输出**作为输入，前序阶段无法流式（会产生不完整输入）。只有最终输出可以直接给用户，因此最后一级流式，兼顾性能与正确性。

## 6. 扩展点

- **新路由策略**：在 `_sort_by_strategy` 增加分支 + 前端下拉选项
- **新编排模式**：`orchestrate.py` 增加 `run_<mode>_stream`，`parse_pipeline` 注册新 mode
- **新渠道模板**：`provider_templates` 表插入记录即可，前端模板页自动展示
- **额度追踪（渠道级每日限额）**：`providers` 表加 `daily_quota/used_today` 字段，`pick_available_models` 过滤超限渠道
